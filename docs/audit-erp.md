# Audit technique et fonctionnel complet, e-System Church, ERP ecclésiastique

- **Date :** 11 novembre 2026
- **Tête auditée :** `0741450b1c80a1d27f5768ae1074119cf314b3fd` (fusion PR #27, US3 attestations)
- **Dépôt :** `axelanibe/e-system-church`, cloné en local, lecture seule
- **Stack :** une seule application Flutter, même `main.dart`, API Fastify + TypeScript, PostgreSQL, API Render https://e-system-church.onrender.com
- **Méthode :** audit statique du code réel, route + écran + table. Aucune exécution, aucune modification, aucune poussée, aucune branche, aucune PR. « Fonctionnel et vérifié » veut dire prouvé dans le code, pas testé en direct sur le serveur ni sur un téléphone.

## Les trois lacunes les plus importantes

1. **Confidentialité pastorale et financière inversée, RBAC non granulaire.** Un trésorier et un simple membre peuvent lire les parcours, les visites avec comptes rendus et les accompagnements, `pastoral.ts:36,61,87`, lecture `READ_ALL`, `GET` générique sans filtre par membre. Un `PATCH` générique sur `depenses` contourne la validation en deux temps, `finances.ts:75-103`. Le rapport consolidé détaillé renvoie les transactions nominatives des antennes, `rapports.ts:235-236`, contre la promesse de `db/schema.sql:288-292`.
2. **Aucune sauvegarde automatique, aucune restauration testée, aucune synchronisation hors ligne, aucune notification.** Zéro occurrence de `backup`, `pg_dump`, `offline`, `sqflite`, FCM ou push dans le dépôt. 3. **Départements = catalogue, pas des espaces de travail, et gouvernance absente.** 16 départements amorcés, affectations et responsables, mais un seul module de travail réel et partiel, Enfants et jeunesse, et aucun espace par département avec membres, activités, réunions, objectifs et rapports.
